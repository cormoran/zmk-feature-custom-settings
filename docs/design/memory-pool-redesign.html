推奨案現在の機能メモリの内訳構造更新手順削減見込み移行・検証根拠

01 · 推奨する方向

共有する対象を、大きな値からすべての可変長値・keyspace のキー・可変長配列要素へ広げる。同時に、配列と keyspace が持つ大きな汎用構造体をなくす。

常時使うものを小さく

INT32 / BOOL / BEHAVIOR は型のサイズで保持。配列は型付き連続領域。メタデータ・既定値・制約は小さな ROM 表現にする。

たまに行う処理に仕事を寄せる

可変長データを詰め直す処理は起動と設定操作に限定。編集用 workspace は同時に一つを貸し出し、通常のキー処理では確保・移動しない。

前提の具体化: サイズ変更は起動、Web UI の write/import/create/delete に加え、その操作に伴う discard/reset・既定値更新・Flash 再読み込みを「設定操作」として処理する。既存の firmware API も同じ経路を通す。入力処理からの固定サイズ更新は維持し、可変長更新を必要とする呼び出しは worker に委譲する。

「空の pool 領域は未使用」でも、静的配列の予約 RAM は減りません。リンク時 RAM を減らすには、複数の最大サイズ予約を一つの総予算へまとめ、その総予算を小さくする必要があります。全設定の最大値を同時に保持する保証を残す場合、payload の最悪時予算は減らせません。

04 · 新しい内部構造

A. descriptor を値から分離する

INT32 / BOOL / BEHAVIOR の live state は型ごとに必要な値 + flags。runtime default を変更しない設定には default_override pointer を置かず、利用する設定だけの拡張表にする。BOOL だけなら byte 単位で十分で、bit packing の Flash コストを払うかは計測後に決める。

既定値は const int32_t、const bool、const binding、blob の pointer + length。range は型別 min/max、options は型別配列と label 参照、制約なしは count=0。ROM に carrier を展開しない。keyspace の不変情報も ROM へ移す。

B. 配列は型付き、動的 entry は小さな slot

INT32 配列は int32_t values[N]、BOOL は byte 配列、BEHAVIOR は 12 B の要素配列。dirty / persistent はそれぞれ bitset。最初は最大 N の領域を固定確保し、pool 上での配列再配置や alignment を増やさずに大きな削減を得る。STRING / BYTES 配列だけ offset/length 表 + shared pool とする。

keyspace は親から type / constraints / permissions を引く。ordinal_name は保存時に生成し、常設しない。各 slot は下記の 16 B 案に縮小できる。pool 内の payload は引き続き [key NUL][payload] とし、保存 adapter を単純にする。

// 設計スケッチ。pool と entry 数は 16-bit 範囲内に制限する。
struct blob_slot {                 // 16 B を目標 (ARM32)
    uint16_t offset, length;        // pool 内の位置 / 格納 byte 数
    uint16_t next, key_len;         // address 順 list / key prefix の長さ
    uint32_t generation;           // delete / reuse で更新
    uint8_t flags, temp_slot;
    uint16_t reserved;
};
struct setting_ref {               // 12 B (owner pointer は ARM32)
    const struct schema *owner;    // static setting / array / keyspace の親
    uint32_t index;                // scalar=0、array index、keyspace ordinal
    uint32_t generation;
};

offset の sentinel、容量、length の加算を検査し、pool 容量は 65,535 B 未満に制限する。大きい構成が必要なら 32-bit layout を選ぶ。世代 wrap 時は slot を退役させる等、古い handle と一致させない。array handle は「その index」の意味とし、insert/remove 後も index は維持、範囲外はエラー。keyspace の delete/reuse は世代不一致で拒否する。

これにより 16 個の array view cache が不要になる。通知や chunk session にも pointer ではなく handle を保存する。queue が設定削除後に処理されても、別の設定へ誤配送しない。削除通知は消えた値への参照ではなく、必要な key/source の小さな snapshot を別途所有する。

C. shared pool の範囲を広げる

plain BYTES/STRING、keyspace、可変長配列要素を同じ allocator へ通す。既定値と同じ未変更 blob は ROM を参照し、最初の変更で pool にコピーする。MEMORY write の dirty は値が default と等しくても保持できるので、値の保存場所と dirty を分離する。

まず一つの byte pool を標準にする。モジュールごとの予約保証が必要なら、少数の pool または quota を宣言できるようにする。全域共有では、一つの keyspace の肥大化が他の設定を圧迫するため、保証が必要な容量まで過剰共有しない。

payload を address 順に保つ slot-index list で管理し、増大時の走査を O(M + B) にする。削除は穴を残し、次の増大で compact。slot table は移動しない。pool を横断して保持する生 pointer は禁止し、read_into または短い locked visitor を使う。allocator に任意長 heap・block header・free-list を追加する必要はない。

D. workspace は値の pool と役割を分けて共有する

chunk 受信、起動 load、keyspace 組み立て、record encode の scratch を、明示的に貸し出す共通 edit workspace に集約する。通常の record read は pool/ROM slice から decode し、編集 session に占有された workspace を必要としない。全 read を編集待ちにしない。

単に C の union に重ねるだけでは不十分。chunk input を保持したまま converter output を作る処理などは同時に二つの領域を要する。必要量は「最大値」ではなく、各 phase で同時に生きる領域の合計の最大値。worker を直列化し、nested 呼び出しには同じ transaction context の subspan を渡す。

workspace を live pool の未使用部分から借りる方式は、満杯時の値変更ができなくなる。推奨の初期実装は live budget P と workspace budget W の独立した静的予約。RAM は P+W として数え、W を「操作中だけ使うのでゼロ」と数えない。TEMPORARY は寿命が長く編集と重なるので、最初は既存の小さな別 pool を維持する。

05 · 変更が少ない前提を、安全な更新手順に落とす

  1. Begin: writer を一つに限定。所有者（local RPC / relay / boot）・target handle・version・mode・wire length を記録。別 writer は queue または -EBUSY。切断、timeout、reset、delete で中断し、確保した workspace を解放する。
  2. Receive / decode: offset の連続性と累積上限を確認。入力は workspace へ。生 pool pointer を source にした更新も、compact 前にここへ snapshot する。converter が必要なら input と output の重ならない span を予約する。
  3. Validate / preflight: 型、制約、文字列終端、key、権限、handle 世代、開始後の対象 value version を再確認。live_used − old_extent + new_extent ≤ P と workspace 上限を検査。失敗したら値・dirty・TEMPORARY・Flash を変更しない。
  4. Persist（PERSIST 時）: 推奨契約は staged value を保存して成功してから publish。保存失敗時は RAM の旧値を維持。現在の一部経路は RAM 更新後に保存するため、この変更は API 契約の変更として明示する。preflight から publish まで対象を予約し、同じ対象への固定サイズ write・delete・reset も待機または拒否する。Flash driver / settings callback が settings lock を再取得しない専用経路を用意する。
  5. Publish: settings lock 下で旧領域を除いて compact、staged value を copy、offset/length/flags を更新。preflight 後は追加確保や失敗し得る converter を呼ばない。MEMORY は dirty、PERSIST 成功は clean、TEMPORARY は base を変えない。
  6. Finish: lock 解放後に通知。中断を含め workspace を返す。別設定への固定サイズ更新は可能でも、同じ対象への更新は version 検査で検出し再試行する。

writer admission → 短い settings lock の順序に統一し、settings lock を持ったまま admission を待たない。Flash I/O 中は read が旧値を読める設計とし、他 writer を admission で止める。通知や visitor の中から可変長編集を再入させない。

Flash 保存の失敗・電源断の耐性は backend の保証に従う。一設定の publish と、配列 _size + 複数要素 / scope / JSON import の全体 atomicity は別問題。初期案は一設定ずつ処理し、成功件数と失敗を返す。全体 rollback や二重の全設定イメージは設けない。

pool が満杯でも置換を可能にする

起動時も同じ検証を通し、部分読み込み・不正データ・容量不足は entry 単位で扱う。pool を更新で縮小した場合、過去の全値が収まる保証はなくなる。既存方針に合わせ警告して読み飛ばし、起動は継続、元の Flash record は勝手に削除しない。ロード順に依存する回復を避けたい製品では、ordinal 順の二段階 load と予算検査を追加する。

07 · 実装する順序と合格条件

段階実装範囲確認すべきこと
0 · 基準測定同じ board、compiler、依存 commit と .config を固定。disabled/minimal/RPC/split と典型 workload を保存。ELF/map から .text/.rodata/.data/.bss、symbol 別差分。main / low-priority / RPC stack の high-water と worst call chain。

2 · handle 化keyspace slot と array view、queue/session、consumer を移行。旧 pointer adapter は過渡期だけ残す。delete/recreate、遅延通知、16 個超の array index、temp owner、世代不一致、index 移動、全外部利用箇所。
3 · pool 拡大blob を共通 allocator、ROM default fallback、address 順 compact。空/満杯/縮小/増大/alias input/NUL、複数 keyspace と array 混在、失敗で旧値維持。使用量計算の overflow、最大 offset。

5 · 旧経路撤去互換 adapter と重複 codec を削除。不要機能の link 残存を確認。同じ機能を有効にした最終 ELF で RAM/Flash 比較。Web UI import/export、split、公式 reset、実機応答と stack headroom。

互換性の線引き:初期版は RPC proto と settings の key/encoding を維持する。内部 API と登録 macro は変更を許容し、段階的に consumer を移行する。storage の変更は別 PR と migration test が必要。Flash に現れる ordinal は handle generation から独立させる。

今回確認した consumer zmk-feature-runtime-macro（ローカル snapshot 4be46f3）は、keyspace の slots[slot].setting や pool に直接アクセスしています。旧設計文書の「DEFINE / POOLED しか利用しない」という前提は使えません。slot 取得・列挙・使用量・公開 key を扱う accessor へ移す必要があります。runtime macro の再生用 copy buffer は consumer の別予算であり、本提案の削減に含めません。[7]

採否の基準: 機能を無効化して見かけの削減を作らない。まず RAM の確実な削減を確認し、Flash 増加があればサイズと理由を提示する。main stack の既定値 2,048 B は過去の boot overflow 対策なので、scratch を移しただけで減らさず、実機・最大保存値・split 負荷で余裕を確認する。

比較した代替案

固定長 slab は移動不要ですが、小さな文字列と大きな macro の混在では内部の余りが増えます。汎用 heap は allocator metadata と断片化の管理が必要です。live 全体の二重 buffer は publish を簡単にする代わりに RAM を二倍近く使います。本件では更新頻度が低いため、小さな不動 slot + compact できる共有 byte pool + 一設定分の workspaceが最も直接的です。

ARM layout 確認の再現手順

基準 commit のヘッダーから value/state/descriptor/constraint/array_state/large_pool/keyspace/slot の型定義と、それらが参照する enum/型を抽出する。array_view_slot は array.c の定義を使う。外部 event 宣言や Zephyr registration macro の展開は不要。標準の stdint/stddef/stdbool は ARM toolchain のものを使う。構造体の field は変更しない。

# VALUE_MAX_SIZE=64、KEY_MAX_LEN=48 を定義した layout.c に
# char size_value[sizeof(struct zmk_custom_setting_value)]; 等を置く。
arm-zephyr-eabi-gcc -mcpu=cortex-m4 -mthumb -mabi=aapcs \
  -std=c11 -c layout.c -o layout.o
arm-zephyr-eabi-nm -S --radix=d layout.o
# value=76 state=24 descriptor=52 constraint=156 array_state=32
# array_view_slot=80 keyspace_slot=144 keyspace=52 large_pool=12

この方法は型レイアウトだけを検査する。実際の macro 展開後に linker が残す object の数や section alignment、最適化による dedup、Zephyr kernel の管理領域、stack 予約量は firmware ELF で別途確認する。
